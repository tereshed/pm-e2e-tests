## Наблюдения вне мандата

- **Несмерженный отчётный MR прошлого прогона.** Шаг 0 (`git fetch` с
  дефолтным конфигом) на первом проходе `git branch -r` показал только
  `origin/main` — локальная копия была настроена как single-branch clone
  (`fetch = +refs/heads/main:refs/remotes/origin/main` в `.git/config`, без
  wildcard). Расширил refspec на `+refs/heads/*:refs/remotes/origin/*` и
  перефетчил — тогда обнаружились более десятка веток на сервере, включая
  `task/2e9f500c-e2e-1a2c6b6-gh-32823241177-1` с отчётом
  `runs/2026-08-25-gh-32823241177-1.md` (run gh-32823241177-1, revision
  `1a2c6b6`), не попавшим в `runs/INDEX.md`. Смержил его в `main` (без
  конфликтов), запушил, удалил ветку. Похоже, что мой непосредственный
  предшественник либо использовал такой же ограниченный clone и не увидел
  собственную ветку на шаге 0 (сам создал и не заметил, что не смержено —
  маловероятно, шаг 0 мержит ЧУЖИЕ ветки), либо его ветка попала на сервер уже
  после того, как следующий (за ним) прогон прошёл шаг 0. Разбираться в
  причине вне мандата, фиксирую разрыв летописи и сам факт, что single-branch
  clone — воспроизводимая ловушка для шага 0: если её не заметить, «раннер
  следующего прогона мержит прошлые» не работает вообще, потому что раннер
  физически не видит чужие ветки.
- **Остальные обнаруженные ветки — не отчётные, не трогал.** Проверил
  `git log origin/main..origin/<ветка> --name-only -- runs/` для всех веток,
